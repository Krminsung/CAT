# [cat][P13] 통합·이관·사용 문서

## 범위

P12가 병합된 main에서 기능 matrix의 누락 연결을 한 차례 정리하고, 사용자가 직접 실행하는 기존
`.smileserv` 데이터의 비파괴 import와 한국어 사용 문서를 완성한다. 새 기능을 탐색하거나 실제 사용자
HOME을 읽지 않으며 앱·원격 provider·MCP·hook·이관 runtime은 실행하지 않는다.

P12는 검토 head `63e094ef314690731fb4c504d91ce4616487e655`를 PR #12에서 merge commit
`c3481e50dc0b5a8b9862d3a185cf7dd8d4f33859`로 병합했다. merge parent는
`05a02e75e795e8079b318b2168fc372c50025c7b`, `63e094ef314690731fb4c504d91ce4616487e655`이며
phase head와 merge tree는 `ec1ac37493f7408c2a40c7865012c5d68e282f87`로 같다. phase head 조상
관계와 `origin/main` 포함을 확인했고 병합 뒤 검사를 반복하지 않았다.

## P13.1 기능 matrix

- `BUILTIN_TOOL_NAMES` 18개와 실제 registry를 대조했다. read 3개, mutation 3개, agent control 2개,
  skill 1개, public web 2개, command/task 4개, MCP 관리 3개다.
- 비대화형 `--print`에서는 `request_user_input`만 등록하지 않아 registry가 17개가 되던 누락을
  보완한다. 이제 항상 등록하되 입력 port가 없으면 `user_input_unavailable`, `not_started`로 실패한다.
- slash 이름·정의·handler는 28개, capability는 12개다. 제품 조립 시 active 목록을 기준 상수와
  대조한다.
- provider 13개는 profile ID 상수와 exhaustive catalog, hook 8개는 event 상수와 앱/tool/stop 호출
  경계, MCP protocol 2개는 config·CLI·adapter factory가 같은 상수를 사용하는지 확인했다.
- CLI agent 옵션과 현재 `auth`, `mcp`, `worktree`, `ssh` 관리 dispatch가 실제 application controller로
  이어지는지 확인했다. legacy import 관리 진입점은 P13.2에서 추가한다.
- 자세한 이름과 구현 경계는 `docs/implementation/CONTRACTS.md`에 기록했다.

## P13.2 비파괴 legacy import

- `cat-tui migrate` 관리 명령을 추가했다. `--source`는 절대 경로만 받고 기본값은 실행 사용자의
  `~/.smileserv`다. source와 `CAT_HOME`이 같거나 중첩되면 원본 변경 가능성을 피하려고 중단한다.
- source root identity·소유권·private mode, credential/settings JSON과 session JSONL의 파일
  종류·symlink·크기·변경 여부를 bounded reader로 확인한다. credential·session 자료에는 private mode도
  요구한다. 이관 구현에는 source write/chmod/rename/unlink 경로가 없다.
- 설정은 대상 파일이 없을 때만 안전한 호환 subset을 새 schema로 쓴다. `permissionMode`,
  `allowedTools`, 승인, hook, MCP 실행 설정은 자동 이관하지 않고 원본에 남긴다.
- `tools`와 기존 `deniedTools`는 현재 built-in 18개의 정확한 이름만 남겨, 함께 이관하지 않는 MCP
  설정의 동적 도구나 알 수 없는 이름이 새 설정을 사용할 수 없게 만들지 않도록 했다.
- 기본 명령은 legacy credential 파일 내용을 읽지 않는다. `--include-credentials`가 있을 때만 두
  credential 파일을 읽는다. API key 후보를 오류 redactor에 먼저 등록하고 13-provider catalog, HTTPS
  endpoint와 공개 field secret 분리 규칙에 맞는 profile만 만든다. 동일 이름의 대상 profile은
  덮어쓰지 않으며 외부 API 검증을 호출하지 않는다.
- legacy session은 source identity와 원본 ID에서 만든 결정적 `legacy_*` ID로 import한다. 대상 index나
  transcript와 충돌하면 건너뛰며 writer lock 안에서 transcript 경로를 다시 확인한다. model history에
  전달된 user/assistant는 새 message schema로 변환하고, 숨김·미전달·도구 사용 중간 응답을 포함한 다른
  record는 `legacy_record` event로 보존한다. 새 wrapper 여유를 포함해 source/세션/전체 깊이·node·크기와
  record 수를 제한한다.
- `trusted-workspaces.json`과 기존 approval은 읽어 새 저장소에 쓰지 않는다. 결과 문구에도 trust·승인
  미이관과 원본 불변을 표시한다.
- 실제 사용자 HOME, 이관 command, credential, session runtime과 검증 명령은 실행하지 않았다.

## P13.3 한국어 사용 문서

- 루트 `README.md`를 소스 checkout의 Node/npm 준비, 현재 `cat-tui` 실행 이름, 빠른 시작과 API key
  profile 설정 순서부터 읽을 수 있도록 작성했다. P14 전에는 npm 없는 launcher·배포 artifact가 없다는
  현재 상태를 설치 안내와 분리해 표시했다.
- 13개 provider, agent CLI 옵션·제약, 5개 관리 진입점, MCP protocol, worktree와 SSH 경계를 실제
  help/dispatcher와 대조해 기록했다.
- TUI 단축키와 slash 명령 28개, built-in 도구 18개를 기준 상수 순서와 연결 범위에 맞춰 정리했다.
- `ask`, `auto-edit`, `full-auto`, `plan`의 자동 허용 차이와 항상 남는 hard deny·trust·path·secret
  경계, non-interactive 승인 제한과 project customization trust 흐름을 설명했다.
- `CAT_HOME` 사용자 자료, project 설정·commands·skills, 설정 precedence, secret 저장 금지와 session
  JSONL 경계를 정리하고 P13.2의 opt-in credential 이관·미이관 항목·충돌 정책을 함께 안내했다.
- 정적 검사만 수행했고 runtime은 미검증이라는 문구와 provider/MCP/web/rewind/process/clipboard,
  P14 설치본·license 제한을 별도 절에 명시했다. README 작성 중 앱이나 명령은 실행하지 않았다.

## P13.4 통합·출처 정리

- 제품 source와 README의 제품명·단계 문구를 검색해, 과거 P09가 아직 활성화 전이라고 안내하던 slash
  fallback 3개와 tool/budget 주석을 현재 capability 의미로 고쳤다. 사용자 README에서는 내부 P14 번호를
  제거하되 아직 배포본이 없다는 사실은 유지했다.
- CLI 관리 명령의 union과 별도 Set에 이름을 두 번 적던 구성을 `CLI_MANAGEMENT_COMMANDS` tuple 하나에서
  type과 parser Set을 파생하도록 정리했다. built-in 18개, slash 28개, provider 13개, hook 8개, MCP
  protocol 2개는 이미 단일 기준 또는 exact/exhaustive 검사가 있어 중복 registry를 새로 만들지 않았다.
- secret 형태 fixture는 발견되지 않았다. 남은 Smile Code·`.smileserv`·기존 환경변수와 fallback 파일명은
  legacy import, 민감 경로 보호와 provenance에 필요한 호환 표식으로 분류해 보존했다.
- P13.2의 session writer release와 profile 저장 실패 시 새 credential 제거, source read-only 경로를
  다시 확인했다. 빈 성공 handler, dead stub 또는 이번 diff에서 새로 누락된 cleanup은 발견되지 않았다.
- 이관 선택의 보안·호환 우선순위를 `DECISIONS.md`, 보존한 legacy 문자열의 범위를 `PROVENANCE.md`에
  기록했다. 실제 앱, 외부 서비스, 사용자 자료와 검증 명령은 실행하지 않았다.

## 전체 정적 코드 검토

P13.1–P13.4를 커밋한 뒤 base `c3481e50dc0b5a8b9862d3a185cf7dd8d4f33859`부터 전체 diff의
registry·entrypoint, 이관 입력·경로·secret·저장 형식, 사용자 문서와 출처 범위를 한 차례 읽었다.
검토에서 legacy 설정의 알 수 없는 도구 이름, target catalog와 어긋나는 provider protocol, API key가
공개 profile·설정 또는 검증 전 오류에 노출되는 경계, source JSON을 새 transcript wrapper로 감쌀 때의
깊이·node 여유, writer lock 획득 사이의 transcript 충돌과 `CAT_HOME` 제어 문자·크기 제한을 확인해 한
묶음으로 보완했다. `__proto__` 같은 JSON field도 일반 객체 assignment를 거치지 않고 보존하도록 했고,
이 변경은 `72bcd74bee47c9d4a4a9472ad179ae46eaa5b4f4`에서 확정했다.

source에는 write, rename, chmod, unlink가 없고 trust·approval·자동 허용·hook·MCP 실행 설정은 여전히
이관하지 않는다. `origin/main`은 P13 base와 같고 base가 현재 detached 작업의 조상임을 확인했다. diff
형식 검사는 깨끗하다. 앱, 이관 command, 실제 사용자 HOME, provider·MCP·hook·도구 runtime과 검증
명령은 실행하지 않았다.
