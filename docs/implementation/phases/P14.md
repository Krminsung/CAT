# [cat][P14] 배포 컴파일·설치본

## 범위

P13이 병합된 main에서 내부 launcher, 고정 Node.js runtime manifest, 비재귀 packager와 비파괴 사용자
영역 installer를 구현한다. 모든 컴파일 입력을 고정한 뒤 `npm run build`를 단 한 번 실행하고, 그
`dist/`를 실행하지 않은 채 Linux x64/arm64 설치본으로 한 번 포장한다. 설치본·앱·Node bundle은 개발
중 실행하지 않으며 npm publish, GitHub Release와 공개 배포는 범위에 포함하지 않는다.

P13은 검토 head `471c5d3b597a5f89a3fccf1303c6f47e86b0b6c4`를 PR #13에서 merge commit
`7d1cc7809871bb09bf704daab71a73299233f7c3`으로 병합했다. merge parent는
`c3481e50dc0b5a8b9862d3a185cf7dd8d4f33859`, `471c5d3b597a5f89a3fccf1303c6f47e86b0b6c4`이며
phase head와 merge tree는 `591530b57ea8e1e1decbce6e2ede8664631833ff`로 같다. phase head 조상
관계와 `origin/main` 포함을 확인했고 병합 뒤 검사를 반복하지 않았다.

## P14.1 launcher와 runtime manifest

- npm 기본 bin은 Unix 기본 도구와 충돌하지 않는 `cat-tui`이고 설치 디렉터리 안의 실제 wrapper는
  `bin/cat`이다. PATH의 `cat` 연결은 installer에서 사용자가 별도로 선택할 때만 고려한다.
- wrapper는 최대 40개의 심볼릭 링크만 해석하고 설치 루트의 `dist/cli/main.js`만 실행한다. 설치본의
  `.runtime/node/bin/node`를 우선하며 소스 checkout에서는 package engine과 같은 Node.js 22.19.0
  이상만 허용한다. 내부 파일을 읽기 위해 시스템 `cat` 명령을 호출하지 않는다.
- bundle runtime은 Node.js 공식 자료에서 2026-09-11 현재 LTS로 표시된 v24.21.0(Krypton)으로
  고정했다. Linux x64와 arm64의 공식 `tar.xz` 파일명·정확한 URL·SHA-256을
  `packaging/runtime-manifest.json`에 기록했고 개발용 engine과 bundle runtime을 분리했다.
- 확인 출처: `https://nodejs.org/en/about/previous-releases`,
  `https://nodejs.org/download/release/v24.21.0/`,
  `https://nodejs.org/download/release/v24.21.0/SHASUMS256.txt`.
- 시스템 `cat`, Node bundle, 앱과 검증 명령은 실행하지 않았다.

P14.1은 `955d21f406d34eeebcd03b81416f4e8c389f684f`에서 완료했다.

## P14.2 비재귀 packager

- `npm run package:installer`는 `scripts/package-installer.mjs`만 한 번 호출한다. 이 script에는 build,
  typecheck, test, app import/실행, help/version 호출과 npm lifecycle 연결이 없다. `dist/cli/main.js`를
  포함한 고정 입력이 없으면 포장을 시작하지 않고 실패한다.
- application stage의 production dependency는 root와 같은 lockfile로
  `npm ci --ignore-scripts --omit=dev --no-audit --no-fund`를 정확히 한 번만 실행해 준비한다. root
  lockfile의 시작/종료 SHA-256이 달라지면 결과를 게시하지 않는다.
- manifest의 Node version, 공식 HTTPS URL, archive 이름, Linux x64/arm64 대상과 SHA-256을 엄격히
  대조한다. 각 archive는 128MiB와 응답 제한 안에서 내려받고 Content-Length와 고정 checksum이 모두
  맞아야 staging에 들어간다.
- application과 architecture별 공식 runtime archive를 reproducible tar 입력으로 묶고 P14.3의 고정
  installer header에 삽입한다. installer와 sidecar/통합 SHA-256을 모두 임시 publish 경로에 완성한 뒤,
  기존 `artifacts/`를 덮어쓰지 않고 디렉터리 rename으로 한 번만 게시한다.
- packager, production dependency staging, Node 다운로드, tar, 앱과 검증 명령은 아직 실행하지 않았다.

P14.2는 `5fa11970dd9f2ede7a799e626000f148a629886c`에서 완료했다.

## P14.3 비파괴 사용자 영역 installer

- installer는 root/sudo 실행을 거부한다. `CAT_INSTALL_DIR` 기본값은
  `$HOME/.local/lib/cat-agent-cli`, `CAT_BIN_DIR` 기본값은 `$HOME/.local/bin`이며, 둘 다 제어 문자와
  4096-byte 초과 입력을 거부하고 현재 사용자가 소유한 canonical HOME 아래의 겹치지 않는 경로로
  제한한다. shell profile, OS package manager와 전역 npm은 변경하지 않는다.
- host Linux architecture와 설치본 target을 먼저 대조한다. 내장 payload SHA-256을 확인해 임시
  디렉터리에 풀고, 포함된 공식 Node archive도 P14.1의 고정 SHA-256과 대조한 뒤 app staging 안에
  배치한다. Node 실행 파일과 앱 진입점은 파일로만 확인하고 실행하지 않는다.
- 비어 있지 않은 기존 설치 경로는 관리 표식, root package 이름과 일반 파일 launcher가 모두 맞을
  때만 update 대상으로 인정한다. 기존 설치를 같은 filesystem의 임시 backup으로 옮긴 뒤 stage를
  rename하며, 후속 실패·signal에는 새로 만든 link와 새 설치를 격리하고 이전 설치를 복구한다. 복구가
  완전하지 않으면 임시 자료를 삭제하지 않고 수동 복구 경로를 출력한다.
- 기본 user-bin 명령은 `cat-tui`다. `CAT_INSTALL_CAT_COMMAND=1`을 명시했을 때만 user-bin의 `cat`
  link를 시도한다. 두 이름 모두 기존 파일·다른 symlink를 보존하고 충돌을 알리며, `/bin/cat`과
  `/usr/bin/cat`은 검사하거나 변경하지 않는다.
- installer header에는 sudo, package manager 설치, profile 변경과 app/version smoke가 없다.
  installer, payload, Node, 앱과 검증 명령은 실행하지 않았다.

P14.3은 `8cc52845d1c59038789cb8c7c0ad0b91a0522bba`에서 완료했다.

## P14.4 배포 문서와 license

- README의 source checkout과 standalone 경계를 갱신하고 `docs/release/INSTALL.md`에 artifact 확인,
  Linux x64/arm64 host 도구, user-home 경로, 기본 `cat-tui`·선택적 `cat`, 충돌 보존과 rollback을
  정리했다. installer 옆 checksum만으로 배포자 신원을 증명할 수 없다는 한계도 명시한다.
- 프로젝트 자체는 원본 package의 license metadata를 자동 승계하지 않고 `UNLICENSED`를 유지한다.
  `LICENSE`에는 공개 권리 허가가 없음을 기록하고 `THIRD_PARTY_NOTICES.md`에는 production closure
  9개 package의 exact version/license/attribution, 공식 Node runtime license 위치를 정리했다.
- `docs/release/REPRODUCIBILITY.md`에 compiler 입력, 한 번 생성한 `dist/`, packager/header/manifest와
  문서 입력, production `npm ci` 한 번, official runtime hash와 deterministic tar 경계를 기록했다.
  host Node/npm/tar/gzip/xz까지 고정하지 않아 bit-for-bit 결과는 미검증이라고 구분했다.
- `docs/release/RELEASE_NOTES.md`, provenance와 결정 기록에 포함 기능, 공개 배포 제외, 권리와 runtime
  미검증 범위를 남겼다. npm의 package file 목록도 실제 release 입력과 맞췄다.
- 설치본, app/runtime, compiler, packager와 검증 명령은 실행하지 않았다.

P14.4는 `233112132c5d8389eb197454c20328238709746d`에서 완료했다.

## 전체 정적 코드 검토

P14.1–P14.4를 커밋한 뒤 base `7d1cc7809871bb09bf704daab71a73299233f7c3`부터 전체 diff의
launcher, manifest, compiler/package 경계, download/checksum, staging/rollback/path, license와 배포
문서를 한 차례 읽었다. 검토에서 다음 문제를 한 묶음으로 보완했다.

- launcher는 patch까지 숫자인 정확한 3-part Node semver만 허용하고 host뿐 아니라 embedded Node도
  최소 engine을 확인한다.
- packager는 symlink·특수 파일 입력을 거부하고 현재 `src/**/*.ts`에서 예상되는 `.js`, `.js.map`,
  `.d.ts`의 정확한 집합과 `dist/`를 대조한다. package engine/bin/check/build/package lifecycle과 runtime
  manifest 경계를 확인하고 production staging 뒤 배포 package의 script entry를 제거한다. npm이 만든
  상대 symlink는 임시 경로를 박아 넣지 않도록 그대로 복사하며 runtime 다운로드 전체 제한은 5분이다.
- installer는 `chmod`, incoming package 이름과 세 direct production dependency를 확인한다. 설치 parent,
  user-bin, 기존 설치와 staged directory의 device/inode/owner/type identity를 commit 직전에 재확인하고,
  `mv -T` 및 이동 전 상태 예약으로 signal/경쟁 사이에 다른 디렉터리로 중첩되거나 이전 설치가 유실되는
  경로를 차단한다. rollback도 동일 identity가 확인된 새 설치와 link만 되돌린다.
- 별도 license 파일이 없는 npm package까지 파일이 있다고 표현하지 않도록 third-party notice를
  정정하고, 실제 package metadata와 공통 MIT notice의 역할을 구분했다.

이 보완은 `b7f18d8b7abc8f36c3550ba80be148de692b2ab8`에서 확정했다.

`origin/main`은 P14 base와 같고 base가 현재 detached 작업의 조상이다. 단계 diff에는 P14 파일과 P13
병합 기록만 있으며 diff 형식 검사는 깨끗하다. build, dependency staging, Node download, tar, packager,
installer, bundled Node와 앱은 실행하지 않았다.
